## Context

See proposal.md for motivation. `release.toml` performs version/man-page preparation and a `cargo check` hook. `docs/development.md` documents direct version-commit/tag pushes. `.github/workflows/release.yml` is generated by cargo-dist, handles PR planning and tag publishing, and creates the GitHub Release before invoking the three channel publishers. No dedicated formatting/Clippy/test workflow exists. Local refs currently identify `dev` as origin's default; rollout assumes integration moves to `main`.

## Goals / Non-Goals

**Goals:** Native release PR management with one versioning tool, checked tags tied to merged commits, and preserved metadata and distribution.

**Non-Goals:** CLI changes, replacing cargo-dist, automatic PR merging, multiple maintained release lines, or a new publishing/retry framework.

## Decisions

1. **Use release-plz for preparation only.** Add `release-plz.toml` with `git_only = true`, `git_release_enable = false`, `git_tag_enable = false`, `release_always = false`, and `git_tag_name = "v{{ version }}"`. Use existing tags as the baseline, retain locked third-party dependencies, and use Conventional Commits for proposed bumps. For `0.x`, enable `features_always_increment_minor` so features advance the minor version; maintainers review breaking changes before merging. Remove cargo-release configuration and instructions. Do not invoke `release-plz release`: with merge commits it checks out and tags the PR head instead of the checked merge commit.

2. **Tag the checked merge commit explicitly.** Run formatting, Clippy, tests, and metadata checks on PRs and `main` pushes. Only a successful `main` push check invokes release orchestration, with a full-history checkout pinned to the event SHA. Query all PRs associated with that SHA and require exactly one merged PR targeting `main`, with `merge_commit_sha` equal to the event SHA, a `release-plz-` head branch in this repository, and the configured App bot as its author. This supports merge commits and squash merges without allowing ordinary pushes or unmerged PRs to tag. Read the tag version from that checkout's manifest and push a tag explicitly at the event SHA; accept an existing tag only when its peeled commit matches, otherwise fail without changing it. Afterwards create a local `main` branch at the same event SHA before running `release-pr`, which requires a named branch, to prepare the next release. Serialize orchestration with `cancel-in-progress: false` and `queue: max`; GitHub queues at most 100 pending runs, and canceled runs must be rerun by a maintainer. Never advance the checkout to a newer `main` for tagging.

3. **Preserve man-page updates in the release PR.** After `release-pr`, use its documented `pr.head_branch` output to check out the bot branch and run a small stdlib metadata helper. Read the version from its `Cargo.toml`, update the unique `.TH GIT-CA` header, and commit only that file when changed. Reconcile after every bot PR update; preserve the date on a no-op rerun. Use the same helper's read-only check in CI. This avoids modifying the generated publisher or relying on nonexistent replacement hooks.

4. **Use GitHub App installation tokens.** Restrict the App to this repository with Contents and Pull requests write access; workflow jobs mint short-lived tokens using configured App ID/private-key secrets. No protected-branch bypass is needed. Bot branch pushes and tags must trigger CI and the tag publisher; default `GITHUB_TOKEN` tag pushes do not. Keep existing publishing credentials confined to channel publishers.

5. **Retain distribution ownership.** No direct edits to generated `release.yml`; cargo-dist still creates releases and publishes all channels. Keep `scripts/release-local.sh` as a deliberate maintainer fallback, not another version manager. Document that partial publish failures require inspection and rerunning failed channels, not reusing a version for changed artifacts.

References: [release-plz configuration](https://release-plz.dev/docs/config), [release-plz tag target behavior](https://release-plz.dev/docs/usage/release#what-commit-is-released), [release PR outputs and extra commits](https://release-plz.dev/docs/github/output#example-commit-files-to-the-release-pr), [associated PR API](https://docs.github.com/en/rest/commits/commits#list-pull-requests-associated-with-a-commit), [workflow concurrency](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency), [GitHub token event rules](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/trigger-a-workflow#triggering-a-workflow-from-a-workflow).

## Risks / Trade-offs

- Bot PR metadata edits can be overwritten by later preparation → reconcile after every update and require consistency checks on the final PR head.
- New pushes can race with release tagging → pin all release work to the event SHA and serialize orchestration.
- Tags can exist before publishing finishes → distinguish tagging from distribution success; inspect failed channel jobs before recovery.
- Missing App credentials/default-branch setup can prevent automation → document these as rollout prerequisites and verify event handoff in a disposable repository.

## Migration Plan

1. Implement configuration, workflows, metadata helper/check, and documentation in atomic commits; remove `release.toml` only when its metadata behavior is covered.
2. Validate locally and in a disposable repository with dummy publishers: PR updates, merge gating, correct tag SHA, bot-triggered checks, and reruns.
3. Maintainer reconciles pending `dev` work into `main`, changes the default branch, configures App secrets and required checks, and enables automation. Do not delete branches as part of this change.
4. Review the first generated release PR. A real tag/publish is a separate maintainer-authorized release action.
5. Roll back by disabling orchestration and reverting its commits. Keep historical tags/package versions; use the explicit local fallback for distribution recovery.
